## 現状
【結論を先に】あそびばには「分けるべきサーバー」がそもそも存在しない。動いてるのは GitHub Pages（静的CDN）1つと、他人（Google）が運用する Firebase 2プロジェクトだけ。Render/Fly のような自前サーバはゼロ本。

■(A) 配信（ホスティング）の単位 = 1リポ・1Pagesサイトに5ゲームが同居
- リポジトリは1つ: `ankake-web/asobiba`（`git remote -v`）、branch `main`。公開先 `https://ankake-web.github.io/asobiba/`。
- ワークフローも1本だけ: `asobiba/.github/workflows/deploy.yml:5-8`（main への push か手動で発火）→ `npm ci` → `npm run build` → `dist/` まるごとを Pages アーティファクトとして上げる（`deploy.yml:37-48`）。`concurrency: group: pages`（`deploy.yml:17-19`）なのでデプロイは常に直列。
- URLは `/asobiba/games/<slug>/` の形。ハブは相対リンクで各ゲームを開く: `asobiba/index.html:234`（`href="./games/${g.slug}/"`）と `:248`。
- `base: "./"`（`asobiba/vite.config.js:36`）なので、サブパスでもカスタムドメインでも同じ成果物が動く。Service Worker は無し（`sw.js` 不在＝dominion と違いキャッシュ破棄の心配なし）。

■(B) ビルドの単位 = 1回のビルドで5ゲーム全部が再ビルド・再デプロイされる（ただし実害は小さい）
- `asobiba/vite.config.js:10-17` が `games/*/index.html` を自動検出して `rollupOptions.input` に全部突っ込むマルチページ構成。1ゲーム直しても `npm run build` は5ページ全部を作り直し、`dist/` 全体が1つのアーティファクトとして上がる（`deploy.yml:46-48`）。
- ただし**出力は実質分離している**。JSチャンクは content hash 付きでゲームごとに独立:
  - `dist/assets/game-uma-race-DSJWCLbp.js` / `game-back10-BogPksom.js` / `main-zuprmrdk.js` の3つだけ。
  - dice-climb / treasure / spy は `<script>`（非module）でインラインなので**チャンクが1つも出ない**（`games/dice-climb/index.html:406`, `treasure/index.html:498`, `spy/index.html:264`）。実際 `dist/games/dice-climb/index.html` は 40493 バイトでソースと同一サイズ＝素通し。
  - つまり uma-race を直しても back10 のハッシュは変わらない → ユーザーのブラウザキャッシュは効いたまま。「全部再ビルド」の実損は CI 時間と、**1ゲームのビルド失敗で5ゲーム全部のデプロイが止まる（ブラスト半径）**の2点だけ。
- 注意: `dist/games/<slug>/index.html` はスクリプトを `src="../../assets/xxx.js"` で参照する（実測）。つまり各ゲームのフォルダは**自己完結していない**。ディレクトリを切り出してコピーしても動かず、分離するなら再ビルドが必須。
- `copy-game-assets` プラグイン（`vite.config.js:22-33`）が `games/<slug>/assets` を `dist` へ verbatim コピー（uma-race の馬画像など、動的文字列参照でViteが拾えないため）。

■(C) バックエンド = あそびば専用サーバは0本。5ゲーム中2つだけが Firebase を叩く
- **うまうまレース** → Firebase プロジェクト `umauma-737d6`（`games/uma-race/index.html:735-741`）。Firestore + 匿名認証 + App Check(reCAPTCHA v3, サイトキーは `:746`)。初期化は `:793-806`（App Check は try/catch で握りつぶすので失敗しても警告どまり）。
- **BACK10** → Firebase プロジェクト `thegameonline`（`games/back10/index.html:799-807`）。**Firestore のみで認証もApp Checkも無し**（`:809-816`）＝守りは Firestore ルールだけ。
- **ダイス登山 / 押しつけ財宝 / 密書(spy)** → `fetch(` `WebSocket` `http://` を grep して**ヒット0件**。完全ローカル、通信ゼロ。
- Firebase は Google 運用のマネージドサービス＝**起動しっぱなし・コールドスタート無し**。Render無料枠のような15分スリープは無関係。

## 選択肢
### 案1【A+B据え置き】現状維持＋ブラスト半径だけ潰す  （工数 S）
1リポ・1Pages・1ビルドのまま。deploy.yml に「変更されたゲームだけスモークテスト」や、ビルド失敗時に前回の dist を残す保険を足す程度。強いて言えば `paths-ignore` で README だけの変更ではデプロイしない、を追加。

**良い点**
- いま何も壊れていない。Pages は CDN で常時起動、コールドスタート概念が無い
- 出力は既にゲームごとに content hash で分離済み（uma-race を直しても back10 のキャッシュは有効のまま）
- ハブ↔ゲームが同一オリジン・相対パスで完結（`index.html:234`）。リンク切れが起きない
- Firebase の承認済みドメイン登録が1回で済む
- 運用対象が1リポ1ワークフローで一番安い

**悪い点**
- 1ゲームのビルドが壊れると5ゲーム全部のデプロイが止まる
- デプロイが `concurrency: group: pages` で直列（`deploy.yml:17-19`）＝5ゲームを同時にいじると待たされる
- CI時間は毎回5ページぶん（といっても数十秒）

### 案2【A+Bを分離】ゲームごとに別リポ＋別Pagesサイト  （工数 L）
`ankake-web/uma-race`, `ankake-web/back10` … と5リポに割り、それぞれ独立のワークフローで `https://ankake-web.github.io/<game>/` に配信。あそびばのハブだけ別リポに残して絶対URLで各サイトへリンク。

**良い点**
- 1ゲームの事故が他4ゲームを巻き込まない（真の分離）
- デプロイが並列（Pages の concurrency はリポ単位）。5本同時に出せる
- ゲームごとにビルド設定・依存を自由に変えられる（片方だけReact化、など）
- **同じ ankake-web.github.io オリジンなので Firebase の承認済みドメイン再登録は不要**（ドメイン単位の許可のため）

**悪い点**
- リポ5＋ハブ1＝6リポの管理。共通改修（`src/shared/rules.js` `sound.js`）が5回コピペになる
- ハブ→ゲームが別サイト扱いになり、相対リンク（`index.html:234`）を絶対URLに書き換え必要
- `dist/games/*/index.html` が `../../assets/` 参照なので dist の切り貼りでは移行できず、各リポで base とディレクトリ構造を組み直す必要あり
- 戻すのが面倒（一度分けたら再統合コストが高い）
- 得られる実利がブラスト半径とCI並列だけで、体験（速度・可用性）は1ミリも変わらない

### 案3【Bだけ分離】1リポのまま、ゲーム単位でビルド／デプロイを分ける  （工数 M）
リポとPagesサイトは1つのまま、GitHub Actions の `paths` フィルタでゲームごとにジョブを分け、変更されたゲームだけをビルド。Pages は成果物全体を要求するので、正確にやるなら Pages をやめて Cloudflare Pages/Netlify のような部分デプロイ可能な配信先に移すか、`actions/cache` で未変更ゲームの dist を再利用する。

**良い点**
- リポは1つのまま＝共通コードの重複が起きない
- 1ゲームのビルド失敗が他ゲームを巻き込まない（ジョブ分離）
- URL・ハブのリンク構造・Firebase設定を一切触らずに済む

**悪い点**
- GitHub Pages は「サイト全体を1アーティファクトで置き換える」モデルなので、真の部分デプロイができない。キャッシュ復元での擬似的な実装になり複雑
- ワークフローの複雑度が上がる割に、体感差はゼロ（現状でもハッシュ分離でキャッシュは効いている）
- 配信先を Pages 以外へ移すなら、それ自体が案2級の移行コスト

### 案4【Cの集約】他プロジェクトの Render 無料4本を1本に集約する（あそびばは対象外）  （工数 M）
あそびばは自前サーバゼロなので分離も集約も対象外。実際に効くのは catan+100万石・dominion・monster-eater・hellapagos の Render 無料4サービス。これを1つの有料 Starter（$7/月）インスタンスにパス（/catan-lan, /dominion/ws, /me/ws, /socket.io）で相乗りさせて常時起動にする。

**良い点**
- **15分アイドルのスリープが消える＝初回接続の30〜60秒待ちが全ゲームで無くなる**（無料枠のコールドスタートは体験を殺す最大要因）
- hellapagos の「無料はディスク揮発でランキングがリセット」（`hellapagos-web/render.yaml:19-20`）も有料ディスクで解決可能
- 監視・環境変数・ALLOWED_ORIGINS の管理箇所が1つになる
- catan と 100万石が既に1サーバ相乗りで動いている（`catan/render.yaml:22` の name が両リポ同一）＝実績あり

**悪い点**
- 月$7（≒1100円）の固定費。副業の収益がゼロのうちは持ち出し
- 1サービスに集約＝1つ落ちると全ゲームのオンラインが同時に落ちる（今は独立していて障害が分散）
- dominion は `js/net.js:12` にURLハードコード、monster-eater は同一オリジン前提（`ui.js:4196`）でHTML配信も兼ねているため、集約するとクライアント側の修正・再デプロイが要る
- monster-eater は singapore、hellapagos は oregon とリージョンが違う。1本化するとどちらかが遠くなる

## 結論
案1（現状維持）を推す。「独立したサーバーにしたい」の動機がたぶん「1つコケたら全部死ぬのが怖い」「1ゲーム直すたび全部デプロイされるのが気持ち悪い」だと思うが、あそびばに関してはどちらも実害がほぼ出ない構造になっている。配信は GitHub Pages のCDN（常時起動・スリープ無し）、5ゲーム中3つは通信ゼロの完全ローカル（dice-climb/treasure/spy は fetch も WebSocket も0ヒット）、残る2つも Firebase 任せでこちらが管理するサーバは1本も無い。ビルドも「全部再ビルド」に見えて出力は content hash で分かれており（`dist/assets/game-uma-race-*.js` と `game-back10-*.js` は独立）、1ゲーム直しても他ゲームのキャッシュは生きたまま＝ユーザー体験への影響はゼロ。分離で得られるのは「ビルド失敗の巻き込み防止」と「CI並列」だけで、その対価が6リポ管理＋共通コードのコピペ地獄なのは割に合わない。むしろ本当に体験を壊しているのは他プロジェクト側で、Render 無料枠4本（catan共有／dominion／monster-eater／hellapagos）が15分アイドルでスリープ→初回接続に数十秒待たされる。分ける／集約するという話をするなら、あそびばではなくこの4本（案4）に月$7を投じるほうが効く。それでもリスク分離をしたいなら、まず案2をuma-raceだけ試して運用コストを実感してから残りを判断するのが安全。

## 移行時の地雷
- 【Firebase 承認済みドメインはホスト単位・パス無関係】ankake-web.github.io/A/ から ankake-web.github.io/B/ への引っ越しなら承認済みドメインの追加は不要（同一オリジン）。逆にカスタムドメインや Netlify/Vercel/Cloudflare Pages へ移すと `umauma-737d6` と `thegameonline` の両方で Authentication → Settings → 承認済みドメインへ新ホストを追加しないと、うまうまレースの匿名ログインが即死する。README.md:41-47 の記載どおり。
- 【reCAPTCHA v3 / App Check】うまうまレースは `games/uma-race/index.html:746` のサイトキー `6LeJi_osAAAAAHouHTc0RJyG29zmfCKYtGRKC5uP` を使う。reCAPTCHA 管理画面の許可ドメインにも新ホストの登録が要る。ただし `:793-801` で App Check の初期化は try/catch で握りつぶされる実装なので、Firestore 側で App Check の強制(enforce)をONにしていなければ落ちずに動いてしまう＝「動いてるように見えて実は保護が外れている」状態に気づきにくい。移行後は Firebase コンソールで App Check のリクエスト検証状況を必ず確認すること。
- 【dist をコピーして移設してはいけない】`dist/games/<slug>/index.html` はスクリプトを `src="../../assets/game-xxx.js"` で参照する（マルチページ + base:"./" の必然）。ゲームフォルダを別リポのルートに置くとパスが2階層ズレて即404。分離するなら必ず「そのゲーム単体を root にした構成で再ビルド」すること。
- 【Vite の base】現状 `vite.config.js:36` は `base: "./"` なので、`/asobiba/` でもルート直下でもカスタムドメインでもビルドし直さず動く。ここを catan 流の絶対base（`catan/vite.config.ts:24` の `'/catan/'`）に変えると移設のたびに再ビルドが必要になるので、相対のまま維持を推奨。
- 【ハブのリンクは相対】`asobiba/index.html:234` と `:248` が `./games/<slug>/` を指す。ゲームを別サイトへ出すならここを絶対URLに書き換える。書き換え漏れるとハブから404に飛ぶ。
- 【ゲーム内のURLハッシュ】うまうまレースは部屋コードを URL の hash から読む（`games/uma-race/index.html` の `new URL(location.href).hash`）。パス構造を変えても hash は生き残るが、共有済みの招待リンク（旧ドメイン）は当然切れる。旧サイトを消すならリダイレクトを置くこと。
- 【旧リポは生きている】`asobiba/README.md:51` のとおり `ankake-web/umarace` と `ankake-web/thegameonline` は公開したまま残っている。あそびばの動作確認が済んだら引退/リダイレクトを決めないと、Firebase の同じプロジェクトを2サイトから叩き続ける（部屋データが混線する可能性）。
- 【Firebase の設定値は平文で埋まっている】`uma-race/index.html:736-741` と `back10/index.html:800-806` に apiKey 等がそのまま入っている。これはWebアプリでは仕様どおり（秘密ではない）だが、守りは Firestore セキュリティルールと App Check だけ。とくに **BACK10 は匿名認証すら呼んでいない**（`:809-816` は initializeApp と getFirestore のみ）ので、ルールが緩いと誰でも書き込める。移行のタイミングでルールを一度確認しておくこと。
- 【Render 無料プランのコールドスタート】catan/dominion/monster-eater/hellapagos は `plan: free`（各 render.yaml）で、15分アイドルするとスリープ→初回接続で起動に数十秒。とくに monster-eater と hellapagos は**サーバがHTMLも配信している**（`monster-eater/js/ui.js:4196`、`hellapagos-web/packages/server/src/index.ts:27`）ので、スリープ中はページが開くところから待たされる。hellapagos は Pages にもクライアントを置いて回避しており、さらに `packages/client/src/socket.ts:10-14` で `autoConnect: false`（オンラインを選んだときだけ接続）にしてスリープを起こさない工夫をしている＝この2つが無料枠と付き合う定石。
- 【hellapagos の fly.toml は死んでいる】`hellapagos-web/fly.toml:2` は `app = "hellapagos-change-me"` のプレースホルダのまま＝Fly.io には未デプロイ。Render(`render.yaml`) が本番。Docker/Fly 経路を復活させるつもりが無いなら、紛らわしいので消すか README に「未使用」と明記したほうがいい。
- 【100万石は catan の worktree】`100man-goku/.git` は `gitdir: .../catan/.git/worktrees/100man-goku` のファイル。`render.yaml` も catan とバイト同一（`name: catan-lan-server`）なので、Render のサービスは1本を共有している。片方の都合でサーバを再デプロイすると**もう片方の対戦も切れる**。分離したいならサービスを別名で立てて `VITE_LAN_SERVER_URL` を分ける必要がある。
- 【Pages のデプロイが詰まる既知の罠】dominion の PROGRESS §6 に、Pages の公開キューが混むと `deployment_queued` のまま10分でタイムアウトし、さらに失敗したデプロイがゾンビ化して以降を400で弾く現象が記録されている。復旧は `gh api -X POST repos/<owner>/<repo>/pages/deployments/<SHA>/cancel`。リポを増やすとこの罠を踏む機会も増えるので、分離するなら手順を控えておくこと。
- 【あそびばに Service Worker は無い】`asobiba/sw.js` は存在せず `serviceWorker` の登録もゼロ件。dominion のような「client資産を変えたら VERSION を上げる」運用は不要。逆に言えばオフライン動作もしないので、将来PWA化するなら5ゲームで1つのSWにするか個別にするかを先に決めること（分離案を採るなら個別が自然）。
